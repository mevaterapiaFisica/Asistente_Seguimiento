## Bug fix principal — `daysInStage` incorrecto para F6B (y F6C/F6F/F6G)

### Problema
Paciente 1-118779-0 pasó de F6A → F6B el 8/6/26 (1 día atrás) pero mostraba 5 días en F6B.

### Causa raíz
`FollowUpDateParser.GetPrecedingSectionMarker` mapeaba F6B (junto con F6A, F6C, F6F, F6G) al mismo marcador HTML `<!-- f5`:

```csharp
// ANTES — BUG
"F6A" or "F6B" or "F6C" or "F6F" or "F6G" => "<!-- f5",
```

Esto hacía que `daysInStage` para F6B se calculara desde el fin de F5 (Marcación) en lugar de desde la asignación del físico.

### Estructura HTML de SitraMed (tabla de seguimiento)
Cada fila tiene secciones delimitadas por comentarios HTML:
- `<!-- f5 Marcación -->` → fechas de la etapa de Marcación
- `<!-- f6 Planificación -->` → primera fecha = **F. Asignación Resp.** (fecha en que se asigna el físico = fin de F6A = inicio de F6B)
- `<!-- f7 ... -->` → fechas de la etapa siguiente

La columna `<th>F. Asignación Resp.</th>` (bajo el header Planificacion) contiene la fecha exacta que delimita F6A → F6B.

### Fix aplicado (`FollowUpDateParser.cs`)

```csharp
// DESPUÉS — CORRECTO
"F6A" => "<!-- f5",                          // F6A empieza cuando termina F5
"F6B" or "F6C" or "F6F" or "F6G" => "<!-- f6",  // F6B+ empieza cuando termina F6A (F. Asignación Resp.)
```

La primera `<td>` con fecha pura en la sección `<!-- f6` es exactamente la fecha de asignación del físico. El fix aplica tanto al path Playwright como al path regex (ambos llaman a `ExtractStageEntryDate`).

### Estado por etapa

| Etapa | Marcador | Estado |
|-------|----------|--------|
| F3 | `<!-- f3` | ✓ correcto |
| F4 | `<!-- f3` | ✓ correcto |
| F5 | `<!-- f4` | ✓ correcto |
| F6A | `<!-- f5` | ✓ correcto |
| F6B | `<!-- f6` | ✓ **corregido** |
| F6C / F6F / F6G | `<!-- f6` | ✓ **corregido** (usa asignación físico como base, mejor que fin de F5) |
| F7A / F7C | `<!-- f6` | ⚠ potencial problema — toman la **primera** fecha de f6 (asignación físico), no la fecha de aprobación final de F6. Pendiente de investigar. |
